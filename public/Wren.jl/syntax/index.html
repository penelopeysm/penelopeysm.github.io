Syntax and semantics

A Wren model is a Julia function marked with the @wren macro. It mixes regular Julia code with two probabilistic primitives:

  • sample: represents latent parameters
  • observe: represents observations

Function arguments have no special meaning in Wren: they're just quantities that are passed into the model.

sample with distributions

All x ~ y statements are lowered into sample statements.

The simplest case is where you have a random variable drawn from a distribution:

using Wren, Distributions@wren function f()    x ~ Normal()endmodel = f()
Model f
├─ arguments (none)
├─ conditioned (none)
└─ expressions
     x ~ Normal()

This model has a single latent variable, x, drawn from Normal().

Wren uses a concept of accumulators to represent outputs from a model. We'll use a few of Wren's functions to extract information from these; we won't explain them here, but please do see Models for more usage details.

accs = rand_with_logp(model)logprior(accs), loglikelihood(accs), parameters(accs)
(-1.7729359938457918, 0.0, VarNamedTuple(x = 1.306902797182039,))

Here we can see that a value was sampled for x, and that the log-prior (and not log-likelihood) was updated.

Arrays and structs

The left-hand side of a tilde can be either

  • a top-level variable, e.g., x ~ Normal(),
  • a field, e.g., m.x ~ Normal(),
  • an array element, e.g., a[1] ~ Normal(),
  • or chains thereof, e.g., m.a[1].x ~ Normal().

These are all things which can be assigned to in Julia (sometimes called 'lvalues'). Other expressions are not permitted, including literals.

Note that if you have a field or element on the left-hand side, the parent object must already exist. That is, you cannot write m.x ~ Normal() if m is not already defined.

For example, this is permitted since y is an argument to the model function (assuming that y is something that can be indexed into):

using Random@wren function yarg(y)    x ~ Normal()    for i in eachindex(y)        y[i] ~ Normal(x)    endendmy_y = zeros(3)yarg_model = yarg(my_y)rand(Xoshiro(468), yarg_model)

@wren function ydef()    x ~ Normal()    y = zeros(3)    for i in eachindex(y)        y[i] ~ Normal(x)    endendydef_model = ydef()rand(Xoshiro(468), ydef_model)

It should be noted that the two models above are actually semantically equivalent: in both models, all y[i] are latent variables, regardless of whether y is an argument or defined in the model body.

The first version (yarg) is more efficient, as it avoids performing the allocation of y each time the model is run.

using Chairmarks@b rand($yarg_model)
26.979 ns (5 allocs: 176 bytes)
@b rand($ydef_model)
29.337 ns (7 allocs: 256 bytes)

Be aware though that the argument to the model will be mutated! Thus, one can really think of the function argument as a 'scratch' buffer that declares the shape of the latent array, whose contents are not used in any way.

Immutable structs largely behave the same way as top-level variables, and mutable structs follow the same principles as arrays.

Conditioning

Now, we would almost certainly like to progress from the starting point above where everything is a latent variable. To condition on some observed data, we can use the | operator on the model. For example, we can condition on the entire y array in one go:

yarg_model_cond = yarg_model | VarNamedTuple(y=[1.0, 2.0, 3.0])accs = rand_with_logp(Xoshiro(468), yarg_model_cond)logprior(accs), loglikelihood(accs), parameters(accs)
(-0.9215311717037962, -9.332540310127463, VarNamedTuple(x = 0.07200886749732076,))

Now the only latent variable is x, and the y array is observed.

Note that the values in the argument passed to the model are now no longer used! As before, the y model argument only serves to declare the shape of the latent array. When the model is evaluated, it will use the values passed to | instead of the values in the argument.

We can do the exact same with ydef, and in exactly the same way, the definition of y inside the model body will be ignored:

ydef_model_cond = ydef_model | VarNamedTuple(y=[1.0, 2.0, 3.0])accs = rand_with_logp(Xoshiro(468), ydef_model_cond)logprior(accs), loglikelihood(accs), parameters(accs)
(-0.9215311717037962, -9.332540310127463, VarNamedTuple(x = 0.07200886749732076,))

One can perform partial conditioning by only specifying part of the latent array (see the VarNames.jl docs for more details on the @vnt macro):

cond = @vnt begin    @template y = zeros(3)    y[1] := 1.0    y[3] := 3.0endyarg_model_partial_cond = yarg_model | condrand(yarg_model_partial_cond)
VarNamedTuple
├─ x => 1.2520843837476732
└─ y => PartialArray size=(3,) data::Vector{Float64}

Enforced observations

Sometimes you may want to enforce in a model that a quantity is observed. However, you might not be able to provide this information at the time of model definition (for example, this might depend on the value of another variable).

Take for example:

@wren function y_not_obs()    x ~ Normal()    y = x + 1    y ~ Normal()end
y_not_obs (generic function with 1 method)

In this model, even though y is defined in the model, the subsequent statement y ~ Normal() will treat y as a latent variable, and will sample a new value for it, which will certainly not be equal to x + 1:

rand_with_logp(y_not_obs())
AccumulatorTuple with 3 accumulators
├─ Params => Wren.VNTAccumulator{:Params, Wren.GetParams, VarNamedTuple{(:x, :y), Tuple{Float64, Float64}}}(Wren.GetParams(), VarNamedTuple(x = 0.10218069400314476, y = 1.234830509319191))
├─ LogPrior => LogPriorAccumulator(-2.605500706895574)
└─ LogLikelihood => LogLikelihoodAccumulator(0.0)

To force y to be observed, Wren provides a macro @observe:

@wren function y_obs()    x ~ Normal()    y = x + 1    @observe y ~ Normal()endaccs = rand_with_logp(y_obs())
AccumulatorTuple with 3 accumulators
├─ Params => Wren.VNTAccumulator{:Params, Wren.GetParams, VarNamedTuple{(:x,), Tuple{Float64}}}(Wren.GetParams(), VarNamedTuple(x = 1.1438116153039266,))
├─ LogPrior => LogPriorAccumulator(-1.5730910388567616)
└─ LogLikelihood => LogLikelihoodAccumulator(-3.2169026541606875)

We can check that these values are consistent:

loglikelihood(accs) ≈ logdensityof(Normal(), parameters(accs)[@vn(x)] + 1)
true

You can in principle use this to enforce that model arguments are observed:

@wren function yarg_obs(y)    x ~ Normal()    for i in eachindex(y)        @observe y[i] ~ Normal(x)    endendrand(yarg_obs([1.0, 2.0, 3.0]))
VarNamedTuple
└─ x => 0.20536287624014588

However, note that once a statement has been marked with @observe, you cannot 'uncondition' it without modifying the model's stored AST itself.

Batched tilde-statements

One of Wren's unique features is syntax-level batching of tilde-statements. This is done using the @plate macro:

@wren function batched(x, y)    N = length(x)    @plate for i in 1:N        x[i] ~ Normal()        y[i] ~ Normal(x[i])    endendx, y = randn(1000), randn(1000)model = batched(x, y) | VarNamedTuple(y=y)

Plated for-loops have the same semantics as regular for-loops. However, they are automatically lowered into a vectorised form, which is more or less analogous to

x[1:N] ~ MvNormal(Zeros(N), I)y[1:N] ~ MvNormal(x[1:N], I)

When N is large this can lead to significant speedups.

Note that this batching is only valid if each iteration of the loop is independent of the others. By marking a loop with @plate, you are effectively asserting that this is the case. Wren does not verify this for you!

As an example of an invalid use of @plate, consider the following:

@plate for i in 1:N-1    x[i + 1] ~ Normal(x[i])end

This will be lowered into the equivalent of

x[(@. (1:N-1) + 1)] ~ MvNormal(x[1:N-1], I)

which has a different meaning: x[i] is now read before it is written to.

Note that the batching is contingent on Wren knowing what to do with the right-hand side of the expression. Firstly, the right-hand side must be a function call. Secondly, there must be a custom method defined for Wren.batched which dispatches on the function on the right-hand side (in this case, Normal). Unfortunately, this means that it is more or less impossible to batch user functions.

In the case where Wren doesn't know how to batch the right-hand side, it will fall back to a regular product distribution, i.e.,

x[1:N] ~ product_distribution([Normal() for i in 1:N])y[1:N] ~ product_distribution([Normal(x[i]) for i in 1:N])

which guarantees correctness, but might not be as efficient as the vectorised form.

Danger

Plates are a highly experimental feature and might not work in all cases. In particular, please note that:

  • The loop must contain only tilde-statements (@observe tilde-statements are fine). This can in theory be relaxed but is not yet implemented.

  • The loop must be for SYMBOL in EXPR, where SYMBOL is a single variable.

  • The only form of indexing allowed is x[i] (i being the loop variable; x can be any identifier). This can in theory be relaxed to admit more forms, such as x[i, j], x[f(i)], x[y[i]], etc., but this is not yet implemented.

  • Plates will increase allocations and will almost certainly cause slowdowns on small loops.

Manual log-likelihood addition

Wren provides a macro, @addloglikelihood [name=:name] expr, which allows you to manually add expr to the model's log-likelihood.

@wren function manual_likelihood()    x ~ Normal()    @addloglikelihood name=:xsq x^2endrand_with_logp(manual_likelihood())
AccumulatorTuple with 3 accumulators
├─ Params => Wren.VNTAccumulator{:Params, Wren.GetParams, VarNamedTuple{(:x,), Tuple{Float64}}}(Wren.GetParams(), VarNamedTuple(x = -1.2893003129717169,))
├─ LogPrior => LogPriorAccumulator(-1.7500861817191562)
└─ LogLikelihood => LogLikelihoodAccumulator(1.662295297028967)

The name argument is optional and Wren currently does not use it, but hopefully will be wired up to pointwise logdensity calculations in the future.
