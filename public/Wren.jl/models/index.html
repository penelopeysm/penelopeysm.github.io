Working with models

Once you have defined a model you will likely want to do something with it! This page will give you a whirlwind tour of how to work with models.

Before we launch into this, it's worth starting by talking about how Wren stores parameters. At Wren's core are two types: VarName and VarNamedTuple.

VarName is a representation of a variable or part of it, for example: x, x[1], or x.a.

using Wren: @vnvn1 = @vn(x)     # a variable named `x`vn2 = @vn(x[1])  # the first element of a variable named `x`(vn1, vn2)
(x, x[1])

A VarNamedTuple is a mapping of VarNames to values, which has a Dict-like interface. However, it is designed to be much more general and performant than a simple Dict or NamedTuple.

Note

For the full story behind the design of VarNamedTuple, please see the VarNames.jl docs.

Drawing samples

Calling rand(model) gives you a trace, i.e., a collection of variable names and values. Given the above discussion you should not be surprised to learn that the trace is a VarNamedTuple!

using Wren, Distributions, LinearAlgebra@wren function f(y)    x ~ Normal()    @observe y ~ Normal(x + 1)    z ~ MvNormal(zeros(3), I)    return :helloendmodel = f(1.0)trace = rand(model)
VarNamedTuple
├─ x => -1.7534555383519235
└─ z => [0.8589352123880593, 1.0991331818145629, -0.7606342177252466]

To access the values inside the trace, you can index into the VarNamedTuple with a VarName.

trace[@vn(x)]
-1.7534555383519235

This works even if you only want one part of a variable. For example, z is a vector, but we can access z[1] by constructing the appropriate VarName:

trace[@vn(z[1])]
0.8589352123880593

Calculating log-densities

Once you have a VarNamedTuple trace (either from rand, or from another source), you can feed it back into the model to calculate the log-densities:

logjoint(model, trace)
-8.93151292281061

Wren also provides logprior and loglikelihood.

In the workflow we've done, we had to evaluate the model twice: once to generate the trace, and once to calculate the log-density. This seems a bit wasteful: can't we do both at once? Indeed, Wren gives you a function for this:

accs = rand_with_logp(model)
AccumulatorTuple with 3 accumulators
├─ Params => Wren.VNTAccumulator{:Params, Wren.GetParams, VarNamedTuple{(:x, :z), Tuple{Float64, Vector{Float64}}}}(Wren.GetParams(), VarNamedTuple(x = -0.5739093514230149, z = [0.009241245581607143, 1.5605222235932001, 1.1703438526042387]))
├─ LogPrior => LogPriorAccumulator(-5.742949976782432)
└─ LogLikelihood => LogLikelihoodAccumulator(-1.0836245050300657)

which returns a new object, an AccumulatorTuple. You can access the trace with parameters(accs), and the log-density with logjoint(accs).

General evaluation

At this point, you are probably wondering what an AccumulatorTuple is. This is a good point to talk about the general evaluation framework that Wren uses, which is heavily lifted from DynamicPPL.

The entry point for all Wren model evaluation is the evaluate function. It takes exactly four arguments:

  • a model (of course!);
  • a latent source (a specification of how to obtain the values of latent variables);
  • a parameter space (a specification of how variables should be transformed); and
  • a set of accumulators (the outputs of the model which we are interested in).
Note

The latter three arguments directly map to DynamicPPL's initialisation strategies, transform strategies, and accumulators. If you want to read more about that, please see the DynamicPPL docs. (All of that is written by me as well!)

The parameter space argument is slightly more advanced, and we'll leave it for later. For now, suffice it to say that we'll always use OriginalSpace() as this value, which essentially stipulates that all variables should not be transformed.

Let's focus on the other two arguments: the latent source and the accumulators.

A latent source says how to obtain the value of, say, x when evaluating the model. We can either say: 'I don't have one! Please draw a fresh sample of x from the prior':

using Random: XoshiroFromPrior(Xoshiro(468))
FromPrior{Random.Xoshiro}(Random.Xoshiro(0x5fa395d0e57a8f5c, 0xb3842d21011f6dba, 0x543216e3e5d19d37, 0x15962183f819a1a2, 0xb6457a432ea4560b))

or we can say, 'I have one stored in this VarNamedTuple! Please use it':

FromParams(trace)
FromParams{VarNamedTuple{(:x, :z), Tuple{Float64, Vector{Float64}}}, Nothing}(VarNamedTuple(x = -1.7534555383519235, z = [0.8589352123880593, 1.0991331818145629, -0.7606342177252466]), nothing)

An accumulator, on the other hand, is a struct that holds information that is collected during model evaluation. An AccumulatorTuple wraps multiple such objects (with some special magic, which is mostly hidden, to maximise type stability).

accs = Wren.AccumulatorTuple(    Wren.LogPriorAccumulator(),    Wren.LogLikelihoodAccumulator(),    Wren.ParamsAccumulator(),)
AccumulatorTuple with 3 accumulators
├─ LogPrior => LogPriorAccumulator(0.0)
├─ LogLikelihood => LogLikelihoodAccumulator(0.0)
└─ Params => Wren.VNTAccumulator{:Params, Wren.GetParams, VarNamedTuple{(), Tuple{}}}(Wren.GetParams(), VarNamedTuple())

The good thing about this design is that you can choose which accumulators to include: for example, if you aren't interested in the log-density, you can include only the ParamsAccumulator, and the log-density calculations will be skipped entirely.

Now that we have the ingredients, let's put it all together:

retval, accs = evaluate(model, FromParams(trace), OriginalSpace(), accs);
(:hello, AccumulatorTuple{3, @NamedTuple{LogPrior::LogPriorAccumulator{Float64}, LogLikelihood::LogLikelihoodAccumulator{Float64}, Params::Wren.VNTAccumulator{:Params, Wren.GetParams, VarNamedTuple{(:x, :z), Tuple{Float64, Vector{Float64}}}}}}((LogPrior = LogPriorAccumulator(-6.47527122711742), LogLikelihood = LogLikelihoodAccumulator(-2.4562416956931896), Params = Wren.VNTAccumulator{:Params, Wren.GetParams, VarNamedTuple{(:x, :z), Tuple{Float64, Vector{Float64}}}}(Wren.GetParams(), VarNamedTuple(x = -1.7534555383519235, z = [0.8589352123880593, 1.0991331818145629, -0.7606342177252466])))))

evaluate returns a tuple of the model's return value:

retval
:hello

along with a new AccumulatorTuple containing the accumulated values:

accs
AccumulatorTuple with 3 accumulators
├─ LogPrior => LogPriorAccumulator(-6.47527122711742)
├─ LogLikelihood => LogLikelihoodAccumulator(-2.4562416956931896)
└─ Params => Wren.VNTAccumulator{:Params, Wren.GetParams, VarNamedTuple{(:x, :z), Tuple{Float64, Vector{Float64}}}}(Wren.GetParams(), VarNamedTuple(x = -1.7534555383519235, z = [0.8589352123880593, 1.0991331818145629, -0.7606342177252466]))

As hinted at before, Wren then provides a few convenience functions to access the accumulated values, namely logjoint, logprior, loglikelihood, and parameters. Please see their respective docs for more information!

Conditioning

This is in some ways more fundamental, but I had to explain what a VarNamedTuple was first. :-)

To condition a model on some observed data, you can use the | operator:

vnt = VarNamedTuple(y=1.0)@wren function f_orig()    x ~ Normal()    y ~ Normal(x + 1)endcond_model = f_orig() | vnt
Model f_orig
├─ arguments (none)
├─ conditioned
│  └─ y => 1.0
└─ expressions
     x ~ Normal()
     y ~ Normal(x + 1)

or the equivalent condition function:

cond_model = condition(f_orig(), vnt)
Model f_orig
├─ arguments (none)
├─ conditioned
│  └─ y => 1.0
└─ expressions
     x ~ Normal()
     y ~ Normal(x + 1)

Unfortunately, the VarNamedTuples that you use for conditioning will almost certainly not be the same as those drawn from a model. Thus, you will likely have to construct a VarNamedTuple yourself. Better docs on this will hopefully come at some point in time but here are some syntax examples:

# NamedTuple-like syntax.VarNamedTuple(y=1.0, z=zeros(3))# From an AbstractDict{VarName}.VarNamedTuple(Dict(@vn(y) => 1.0, @vn(z.a) => zeros(3)))# With a macro.@vnt begin    # Note the use of `:=` rather than `=`    y := 1.0    z.a := zeros(3)    # This says that `vect[1]` is part of a three-element vector, and that    # its first value is 1.0. The other values of `vect` are NOT part of    # the resulting `VarNamedTuple`. This allows you to condition only part    # of a vector. Note that the template should have the same shape as    # whatever `vect` in the model will be.    @template vect = zeros(3)    vect[1] := 1.0end

Vectorisation

Wren models can be converted into a vectorised form, i.e., one where the parameters are supplied as a vector rather than a VarNamedTuple. This is done with the VecModel constructor, which takes a model and an AbstractADType object:

using Enzymevecmodel = VecModel(model, AutoEnzyme(; mode=Reverse))
VecModel f
├─ adtype => AutoEnzyme(mode=EnzymeCore.ReverseMode{false, false, false, EnzymeCore.FFIABI, false, false}())
├─ dimension => 4
├─ parameter space => UnconstrainedSpace()
└─ Model f
   ├─ arguments
   │  └─ y => 1.0
   ├─ conditioned (none)
   └─ expressions
        x ~ Normal()
        @observe(y ~ Normal(x + 1))
        z ~ MvNormal(zeros(3), I)
        return :hello

If you are only interested in vectorisation and not AD, you can pass nothing as the second argument:

noad_vecmodel = VecModel(model, nothing)
VecModel f
├─ adtype => nothing
├─ dimension => 4
├─ parameter space => UnconstrainedSpace()
└─ Model f
   ├─ arguments
   │  └─ y => 1.0
   ├─ conditioned (none)
   └─ expressions
        x ~ Normal()
        @observe(y ~ Normal(x + 1))
        z ~ MvNormal(zeros(3), I)
        return :hello

This is mostly useful when you want to handoff a Wren model to a different library which expects a vector interface. In particular, VecModels obey the LogDensityProblems.jl interface, and thus can be used with a wide range of other Julia packages that expect this.

You can draw a vectorised sample from a VecModel with the rand function:

v = rand(vecmodel)
4-element Vector{Float64}:
  0.9624847935878895
  0.2527200932160597
  0.41143394149817236
 -0.8112800973254568
import LogDensityProblems as LDPLDP.logdensity(vecmodel, v)               # Works without an adtype.LDP.logdensity_and_gradient(vecmodel, v)  # Requires an adtype.
(-5.966730008935415, [-1.924969587175779, -0.2527200932160597, -0.41143394149817236, 0.8112800973254568])

Wren in fact exports shorter functions for these, namely lp and lp_and_grad, which are directly equivalent to the above. Additionally, Wren provides an in-place gradient lp_and_grad! function, which may be useful for squeezing every last bit of performance out. LogDensityProblems.jl does not provide this (but if you have a good usecase for it, please consider adding a comment on this issue!).

By default, VecModels are always run in UnconstrainedSpace(): that is, all parameters are transformed into a form where they can take any value in ℝ^n. The log-density calculation will then include the log-Jacobian term corresponding to this transfomration. If this is not desired, you can specify a different parameter space, or a different log-density calculation function as a keyword argument to the VecModel constructor: please see its docstring for more info.

Warning

Vectorisation places certain restrictions on the structure of the model. In particular, it is not valid for a model to have a varying dimension. This can be caused either by parameters which have varying sizes, or models which simply have a varying number of parameters:

x ~ Poisson(3.0)y ~ MvNormal(zeros(x), I)  # dimension of `y` is not constantif x > 4    z ~ Normal()  # existence of `z` is not constantend

The set of variable names must also be constant across all model evaluations. Thus, even though the following model has a constant number of parameters, it is still not valid for vectorisation:

x ~ Normal()if x > 0    y ~ Normal()else    z ~ Normal()end

Benchmarking

For the vast majority of users, the easiest way to benchmark will be to use the @bmodel macro:

using Wren, Distributions, LinearAlgebra@wren function f()    x ~ Normal()    z ~ MvNormal(zeros(3), abs(x) * I)end@bmodel f()
ModelRunResult
  ├ model       : f
  ├ backend     : nothing
  ├ n_params    : 4
  ├ rand        : 81.072 ns (9 allocs: 592 bytes)
  ├ logjoint    : 22.539 ns (4 allocs: 160 bytes)
  └ lp          : 28.136 ns (4 allocs: 160 bytes)
using Enzyme@bmodel f() AutoEnzyme(; mode=Reverse)
ModelRunResult
  ├ model       : f
  ├ backend     : AutoEnzyme(mode=EnzymeCore.ReverseMode{false, false, false, EnzymeCore.FFIABI, false, false}())
  ├ n_params    : 4
  ├ rand        : 80.569 ns (9 allocs: 592 bytes)

  ├ lp          : 27.996 ns (4 allocs: 160 bytes)
  ├ lp_and_grad : 69.377 ns (10 allocs: 416 bytes)
  └ grad / lp   : 2.478

If this isn't enough and you want to customise exactly what gets benchmarked, and to test correctness, Wren also provides a function benchmark_and_test which has a staggering number of options. (There are also slightly simpler versions, benchmark_ad, and test_ad.)
