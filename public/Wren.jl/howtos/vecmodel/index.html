Vectorisation

Wren models can be converted into a vectorised form, i.e., one where the parameters are supplied as a vector rather than a VarNamedTuple. This allows Wren models to be used with a wide range of other Julia packages which expect a vectorised interface (i.e., LogDensityProblems.jl).

We begin by setting up our now-familiar eight schools model.

using Wren, Wren.Distsy = [28, 8, -3, 7, -1, 1, 18, 12]sigma = [15, 10, 16, 11, 9, 11, 10, 18]J = 8@wren function eight_schools(y, sigma, J)    mu ~ Normal(0, 5)    tau ~ HalfCauchy(0, 5)    theta ~ MvNormalScale(fill(mu, J), tau * I)    @batch for i in 1:J        @observe y[i] ~ Normal(theta[i], sigma[i])    end    return (mu=mu, tau=tau)endmodel = eight_schools(y, sigma, J)

Introduction

Conceptually, vectorising a model requires two things:

  1. a mapping from the original model's parameters to ranges of indices in a vector; and
  2. transformation from the original model's parameter space to an unconstrained space (i.e., a space where all parameters can take any value in ℝ^n).

The latter is technically not mandatory, but in practice often desirable due to the fact that many inference algorithms work best in unconstrained space.

Vectorisation is done with the VecModel constructor, which takes a model and an ADTypes.AbstractADType object, constructs the above mapping, and stores it. The latter allows you to calculate gradients of the log-density with respect to the vectorised parameters.

using Enzyme# DEFAULT_AD is AutoEnzyme(; mode=Reverse)).vecmodel = VecModel(model, Wren.DEFAULT_AD)

Automatic differentiation

Wren's 'default' AD backend is reverse-mode Enzyme: in general we recommend this for performance.

However, Wren does also use DifferentiationInterface.jl under the hood, so you can pass any AD backend which is supported by DI. These include (but are not limited to) the following. All of the following are re-exported by Wren:

  • AutoEnzyme(; mode=Forward) or AutoEnzyme(; mode=Reverse) using Enzyme.jl;
  • AutoMooncakeForward() or AutoMooncake() using Mooncake.jl.
  • AutoForwardDiff() using ForwardDiff.jl;
  • AutoReverseDiff() using ReverseDiff.jl;
You must explicitly load the AD backend

Because AD functionality is implemented in the form of Julia package extensions, you must explicitly load the AD backend you want to use before creating a VecModel. Wren does not automatically load any AD backend, because this would require Wren to incur a dependency on them.

You can also use AutoReactant to further accelerate the model evaluation using Reactant.jl. Please see the Working with Reactant page for more information.

If you are only interested in vectorisation and not AD, you can pass nothing as the second argument:

noad_vecmodel = VecModel(model, nothing)

Interacting with VecModel

This is mostly useful when you want to hand off a Wren model to a different library which expects a vector interface. In particular, VecModels obey the LogDensityProblems.jl interface, and thus can be used with a wide range of other Julia packages that expect this.

Probably the first thing to do is to draw a vectorised sample from a VecModel with vector_parameters. This draws from the prior of the underlying model:

v = vector_parameters(vecmodel)

Log-prior is untransformed

When calling simulate, the log-prior returned does not include log-Jacobian terms, even if the VecModel was constructed with a transformation to unconstrained space.

Log-densities

In addition to the above interface, VecModels also have a privileged notion of a log-density. That is, unlike the underlying model which tracks each probability component separately and does not emphasise one over the other, VecModels have a single type of log-density which it knows how to calculate.

By default, this log-density is the transformed log-joint: that is, the log-prior plus the log-likelihood, minus the log-Jacobian of the transformation from the original parameter space to the unconstrained space. This is precisely the log-density that is required by many inference algorithms which run in unconstrained space.

The reason for having this single notion of a log-density is to satisfy the LogDensityProblems.jl interface, which expects a mapping from $\mathbb{R}^n$ (parameters) to $\mathbb{R}$ (a single log-density value). If you have a vector of parameters, you can calculate the log-density of these vectorised parameters, and their gradient:

import LogDensityProblems as LDPLDP.logdensity(vecmodel, v)               # Works without an adtype.LDP.logdensity_and_gradient(vecmodel, v)  # Requires an adtype.
(-67.51710207155006, [0.003240414392609803, 2.565743138288633, 0.4630518812845361, 0.01624377524742225, -0.21397143146324174, -0.12810444027046355, 0.08544371917890864, 0.3181045738668181, 0.0027557943772375526, 0.23436471080616975])

Wren in fact exports shorter functions for these, namely lp and lp_and_grad, which are directly equivalent to the above. Additionally, Wren provides an in-place gradient lp_and_grad! function, which may be useful for squeezing every last bit of performance out. Note that LogDensityProblems.jl does not provide a corresponding interface function for lp_and_grad! (but if you have a good usecase for it, please consider adding a comment on this issue!).

Accessing log-density components

If you need to access the log-density components separately when evaluating a VecModel, it is recommended to either use simulate (less efficient) or directly call WrenCore.evaluate with the appropriate accumulators. Documentation on this will be forthcoming but for now please see the source code.

By default, VecModels are always run in UnconstrainedSpace(): that is, all parameters are transformed into a form where they can take any value in ℝ^n. As mentioned above, the log-density calculation will then include the log-Jacobian term corresponding to this transformation. If this is not desired, you can specify a different parameter space, or a different log-density calculation function as a keyword argument to the VecModel constructor: please see its docstring for more info.

Higher-order derivatives

If you have a use for higher-order derivatives like Hessians, please open an issue!

Mutation semantics

Note that, for performance reasons, Wren retains the right to mutate the input vector passed into simulate, logdensity, and other functions. This is subject to the same considerations as outlined in Working with Models.

It's probably worth illustrating this with a simple example. The easiest way to trigger this behaviour is if your model explicitly mutates arrays (e.g. writing x[1] += 1 if x is a parameter).

@wren function with_mutation()    x ~ MvNormalScale(zeros(2), I)    x[1] += 1.0    @info xendvm = VecModel(with_mutation(), nothing)

Each time we run the model, we get a new value of x, and mutate it inside the model. So far, this looks reasonable. However, the following can be quite surprising:

p = [2.0, 3.0]LDP.logdensity(vm, p)p
2-element Vector{Float64}:
 3.0
 3.0

The vector p has been mutated in-place by the x[1] += 1.0 statement.

The results are still correct

There isn't a correctness issue here at all: the log-density is always calculated with respect to the values that are passed in. The slightly surprising thing is that the values that are passed in are themselves mutated.

The reason for this is because lp is a model evaluation, and as discussed in Working with Models, Wren makes no promises to copy anything during model evaluation.

However, it is still always guaranteed that at model construction time the arguments to the model will be copied. This holds true for VecModels as well (if only because to make a VecModel you must first make a Model). The parameter vector p above does not fall into this category: it does not exist at model construction time.

Restrictions

Vectorisation places certain restrictions on the structure of the model. In particular, it is not valid for a model to have a varying dimension. This can be caused either by parameters which have varying sizes:

x ~ Poisson(3.0)y ~ MvNormalScale(zeros(x), I)  # dimension of `y` is not constant

or models which simply have a varying number of parameters:

if x > 4    z ~ Normal()  # existence of `z` is not constantend

Wren contains some code for handling cases where the names of parameters vary but their number is constant, but this is not an official guarantee right now.
