Working with Models

Once you have defined a model, you can use it to draw samples, calculate log-densities, and more.

This page describes Wren's high-level interface for running models and extracting information from them.

To begin, let's define a model with several of the features that Wren supports:

using Wren, Wren.Distsy = [28, 8, -3, 7, -1, 1, 18, 12]sigma = [15, 10, 16, 11, 9, 11, 10, 18]J = 8@wren function eight_schools_centred(y, sigma, J)    mu ~ Normal(0, 5)    tau ~ HalfCauchy(0, 5)    theta_trans ~ MvNormalScale(zeros(J), I)    @gq theta = mu .+ tau .* theta_trans    for i in 1:J        @observe y[i] ~ Normal(theta[i], sigma[i])    end    return (mu=mu, tau=tau)endmodel = eight_schools_centred(y, sigma, J)

The simulate family

The core function that Wren provides for drawing samples from a model is simulate.

Without any arguments, simulate will draw from the prior distribution of the model:

res = simulate(model)
ModelResult

│  ├─ tau => 0.3425873821486953

It returns a ModelResult object which has several fields. To extract these, it is recommended to use the following accessor functions:

  • parameters: returns a VarNamedTuple of the parameters drawn from the model;
  • generated_quantities: returns a VarNamedTuple of the generated quantities that were saved;
  • return_value: the return value (here a NamedTuple with mu and tau);
  • logprior, loglikelihood, and logjoint: the log-density components.

For example:

parameters(res)
VarNamedTuple
├─ mu => -4.111470848022389
├─ tau => 0.3425873821486953
└─ theta_trans => [1.9005911081815283, -1.6376793073055906, 0.8983207202949508, -0.25322325072576557, 0.554738564621684, -0.8276539267905881, 0.13621790094294997, -2.354187100278194]

This VarNamedTuple object can, roughly speaking, be thought of as a mapping from variable names (VarNames) to values. For example, indexing into it works:

parameters(res)[@vn(mu)]
-4.111470848022389

If you want to perform forward simulation but you only want the parameters, you can directly call parameters(model). This will be more performant than parameters(simulate(model)), because it avoids calculating the log-densities. (The other functions behave exactly the same way.)

parameters(model)
VarNamedTuple
├─ mu => -2.5237182573732753
├─ tau => 2.562025218585402
└─ theta_trans => [-1.130387753044382, -0.740998064662882, -1.1311066920579134, 0.04990014857243035, 0.5292933622602668, -0.5454566812504028, 0.95975994187851, -0.5661665498867159]

The functions parameters, generated_quantities, return_value, logprior, loglikelihood, and logjoint can therefore be thought of in the following manner:

  • if you pass it a result of an evaluation, it will extract the corresponding field;
  • if you haven't yet evaluated the model, it will evaluate it and return the corresponding field.

Specifying input sources

While the above is useful for quickly drawing random samples, often we want to control exactly how these values are drawn.

For example, we might want to draw from the prior using a specific RNG seed. You can do this by passing a Random.AbstractRNG to simulate.

using Randomsimulate(model, Xoshiro(468))

General latent sources

From the above, one can see that the RNG seed, or the parameter values, both play the same role: they are sources of latent values for the model. Under the hood, Wren is actually converting these to an AbstractLatentSource object. Indeed, you can construct and pass one of these directly for even more control (for example, you might want to specify some parameters and sample others.)

This is the reason why Wren's API specifies the seed as the second argument: it's because the second argument can be thought of as 'a latent source or something that can be converted to one'.

VarName and VarNamedTuple

At Wren's core are two types: VarName and VarNamedTuple. (If you have used FlexiChains.jl, you may have seen these before.)

VarName is a representation of a variable or part of it, for example: x, x[1], or x.a.

vn1 = @vn(x)     # a variable named `x`vn2 = @vn(x[1])  # the first element of a variable named `x`(vn1, vn2)
(x, x[1])

A VarNamedTuple is a mapping of VarNames to values, which has a Dict-like interface. However, it is designed to be much more general and performant than a simple Dict or NamedTuple.

The most frequent operation you will encounter is indexing into it. Returning to our model above:

vnt = parameters(model)
VarNamedTuple
├─ mu => -0.9030199393471436
├─ tau => 22.529938160966108
└─ theta_trans => [0.3629263130832376, -0.262786265488974, -0.29198471874206783, -0.7536879233329971, -1.4463206437514204, -2.0265916454042525, -0.6515902671853279, -0.5888722221854124]

we can access not only the top-level variables

vnt[@vn(mu)], vnt[@vn(theta_trans)]
(-0.9030199393471436, [0.3629263130832376, -0.262786265488974, -0.29198471874206783, -0.7536879233329971, -1.4463206437514204, -2.0265916454042525, -0.6515902671853279, -0.5888722221854124])

but also parts of variables:

vnt[@vn(theta_trans[1])]
0.3629263130832376

Notice here that @vn(...) describes what we want to access (sort of a 'path' into the data that we're interested in).

Constructing your own VarNamedTuple

Most often end-users who want to set specific values known in advance will want to construct a VarNamedTuple via the VarNames.@vnt macro. If you are writing an inference algorithm which has to work over arbitrary models, you should look at the lower-level interface, including VarNames.templated_setindex!!.

Usually, you will obtain VarNamedTuples from Wren's or FlexiChain's functions, so you will not need to think too much about how to construct them, unless you are writing custom inference algorithms. For this reason, although we would like to have more docs on this in the future, for now we defer a detailed discussion of VarNamedTuple to the VarNames.jl docs.

When does Wren copy arguments?

At this point, since we have been evaluating models a few times, it is an apposite time to discuss when Wren makes copies of the model arguments.

In general, for performance reasons, Wren tries to avoid copying its arguments as far as possible. This means that if you pass a mutable object to Wren, it may be modified in-place during evaluation of a model.

Notice how, for example, x[1] is different on each iteration of the following loop:

@wren function model_with_mutable_arg(x)    @info ("before", x[1])    x[1] ~ Normal(0, 1)    @info ("after", x[1])endmodel = model_with_mutable_arg([0.0])for i in 1:2    simulate(model)end
[ Info: ("before", 0.0)
[ Info: ("after", -0.04967778938292093)
[ Info: ("before", -0.04967778938292093)
[ Info: ("after", -0.5692162000327606)

What happens here is that when a sampling statement is encountered, the resulting value is stored back into x[1]. So the second time the model is evaluated, x[1] will have taken on the value that it was assigned in the first evaluation.

However, to try to minimise potential footguns, Wren will make a copy of arguments at model construction time. The reason why this is permissible is because you will only construct the model once (as opposed to evaluation, which happens many times in performance-sensitive code).

In the following example, we do the same as above, but we give the argument a name so that we can check whether it has been modified:

x_original = [0.0]model = model_with_mutable_arg(x_original)for i in 1:2    simulate(model)end
[ Info: ("before", 0.0)
[ Info: ("after", -0.1009999730602373)
[ Info: ("before", -0.1009999730602373)
[ Info: ("after", -0.014129242496636303)

The behaviour so far is unsurprisingly exactly the same as above, in that x[1] is modified in-place during model evaluation. However, if we check the original array passed into the model, we can see that it has not been modified, as Wren made a copy of it for the model:

x_original
1-element Vector{Float64}:
 0.0
