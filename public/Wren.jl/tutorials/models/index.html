Working with models

Once you have defined a model you will likely want to do something with it! This page will give you a whirlwind tour of how to work with models.

Before we launch into this, it's worth starting by talking about how Wren stores parameters. At Wren's core are two types: VarName and VarNamedTuple.

VarName is a representation of a variable or part of it, for example: x, x[1], or x.a.

using Wren: @vnvn1 = @vn(x)     # a variable named `x`vn2 = @vn(x[1])  # the first element of a variable named `x`(vn1, vn2)
(x, x[1])

A VarNamedTuple is a mapping of VarNames to values, which has a Dict-like interface. However, it is designed to be much more general and performant than a simple Dict or NamedTuple.

Note

For the full story behind the design of VarNamedTuple, please see the VarNames.jl docs.

Drawing samples

Calling parameters(model) gives you a trace, i.e., a collection of variable names and values. Given the above discussion you should not be surprised to learn that the trace is a VarNamedTuple!

using Wren, Distributions, LinearAlgebra@wren function f(y)    x ~ Normal()    @observe y ~ Normal(x + 1)    z ~ MvNormal(zeros(3), I)    return :helloendmodel = f(1.0)trace = parameters(model)
VarNamedTuple
├─ x => 0.016134805476968793
└─ z => [0.05496918942003269, -0.9736045312449976, 1.0483663562229482]

To access the values inside the trace, you can index into the VarNamedTuple with a VarName.

trace[@vn(x)]
0.016134805476968793

This works even if you only want one part of a variable. For example, z is a vector, but we can access z[1] by constructing the appropriate VarName:

trace[@vn(z[1])]
0.05496918942003269

Calculating log-densities

Once you have a VarNamedTuple trace (either from rand, or from another source), you can feed it back into the model to calculate the log-densities:

logjoint(model, trace)
-5.619952703924378

Wren also provides logprior and loglikelihood.

In the workflow we've done, we had to evaluate the model twice: once to generate the trace, and once to calculate the log-density. This seems a bit wasteful: can't we do both at once? Indeed, Wren gives you a function for this:

result = simulate(model)
ModelResult
├─ parameters => VarNamedTuple
│  ├─ x => -1.1526398457990237
│  └─ z => [-0.393984878371682, 0.40031879248126745, -0.19673316994437498]
├─ return_value => :hello
├─ logprior => -4.517135019958276
└─ loglikelihood => -1.5832278402664715

which returns a new object, a ModelResult. You can access the trace with parameters(result), and the log-density with logjoint(result).

General evaluation

This is a good point to talk about the general evaluation framework that Wren uses, which is heavily lifted from DynamicPPL.

The entry point for all Wren model evaluation is the WrenCore.evaluate function. It takes exactly four arguments:

  • a model (of course!);
  • a latent source (a specification of how to obtain the values of latent variables);
  • a parameter space (a specification of how variables should be transformed); and
  • a set of accumulators (the outputs of the model which we are interested in).
Note

The latter three arguments directly map to DynamicPPL's initialisation strategies, transform strategies, and accumulators. If you want to read more about that, please see the DynamicPPL docs. (All of that is written by me as well!)

The parameter space argument is slightly more advanced, and we'll leave it for later. For now, suffice it to say that we'll always use WrenCore.OriginalSpace() as this value, which essentially stipulates that all variables should not be transformed.

Let's focus on the other two arguments: the latent source and the accumulators.

A latent source says how to obtain the value of, say, x when evaluating the model. We can either say: 'I don't have one! Please draw a fresh sample of x from the prior':

using Random: XoshiroFromPrior(Xoshiro(468))
FromPrior{Random.Xoshiro}(Random.Xoshiro(0x5fa395d0e57a8f5c, 0xb3842d21011f6dba, 0x543216e3e5d19d37, 0x15962183f819a1a2, 0xb6457a432ea4560b))

or we can say, 'I have one stored in this VarNamedTuple! Please use it':

FromValues(trace)
FromValues{VarNamedTuple{(:x, :z), Tuple{Float64, Vector{Float64}}}, WrenCore.Void}(VarNamedTuple(x = 0.016134805476968793, z = [0.05496918942003269, -0.9736045312449976, 1.0483663562229482]), WrenCore.Void())

An accumulator, on the other hand, is a struct that holds information that is collected during model evaluation. An AccumulatorTuple wraps multiple such objects (with some special magic, which is mostly hidden, to maximise type stability). Because most users shouldn't really need to reach for these types on a daily basis, we keep them in WrenCore rather than re-exporting them from Wren.

using WrenCore:    AccumulatorTuple, LogPriorAccumulator, LogLikelihoodAccumulator, ParamsAccumulatoraccs =    AccumulatorTuple(LogPriorAccumulator(), LogLikelihoodAccumulator(), ParamsAccumulator())
AccumulatorTuple with 3 accumulators
├─ LogPrior => LogPriorAccumulator(0.0)
├─ LogLikelihood => LogLikelihoodAccumulator(0.0)
└─ Params => WrenCore.VNTAccumulator{:Params, false, WrenCore.GetParams, VarNamedTuple{(), Tuple{}}}(WrenCore.GetParams(), VarNamedTuple())

The good thing about this design is that you can choose which accumulators to include: for example, if you aren't interested in the log-density, you can include only the ParamsAccumulator, and the log-density calculations will be skipped entirely.

Now that we have the ingredients, let's put it all together:

using WrenCore: evaluate, OriginalSpace, EvalContextretval, accs =    evaluate(model, FromValues(trace), OriginalSpace(), accs, EvalContext{false}());
(:hello, AccumulatorTuple{3, @NamedTuple{LogPrior::LogPriorAccumulator{Float64}, LogLikelihood::LogLikelihoodAccumulator{Float64}, Params::WrenCore.VNTAccumulator{:Params, false, WrenCore.GetParams, VarNamedTuple{(:x, :z), Tuple{Float64, Vector{Float64}}}}}}((LogPrior = LogPriorAccumulator(-4.700884004745816), LogLikelihood = LogLikelihoodAccumulator(-0.9190686991785626), Params = WrenCore.VNTAccumulator{:Params, false, WrenCore.GetParams, VarNamedTuple{(:x, :z), Tuple{Float64, Vector{Float64}}}}(WrenCore.GetParams(), VarNamedTuple(x = 0.016134805476968793, z = [0.05496918942003269, -0.9736045312449976, 1.0483663562229482])))))

The last argument, EvalContext, controls whether model arguments are copied during evaluation. This is only needed when differentiating with Enzyme, so you should almost always pass EvalContext{false}() here.

evaluate returns a tuple of the model's return value:

retval
:hello

along with a new AccumulatorTuple containing the accumulated values:

accs
AccumulatorTuple with 3 accumulators
├─ LogPrior => LogPriorAccumulator(-4.700884004745816)
├─ LogLikelihood => LogLikelihoodAccumulator(-0.9190686991785626)
└─ Params => WrenCore.VNTAccumulator{:Params, false, WrenCore.GetParams, VarNamedTuple{(:x, :z), Tuple{Float64, Vector{Float64}}}}(WrenCore.GetParams(), VarNamedTuple(x = 0.016134805476968793, z = [0.05496918942003269, -0.9736045312449976, 1.0483663562229482]))

As hinted at before, Wren then provides a few convenience functions to access the accumulated values, namely logjoint, logprior, loglikelihood, and parameters. Please see their respective docs for more information!

Conditioning

To condition a model on observed data, pass a NamedTuple to the | operator:

observed = (y=1.0,)@wren function f_orig()    x ~ Normal()    y ~ Normal(x + 1)endcond_model = f_orig() | observed
Model f_orig
├─ arguments (none)
├─ conditioned
│  └─ y => 1.0
└─ expressions
     x ~ Normal()
     y ~ Normal(x + 1)

The equivalent function is condition:

cond_model = condition(f_orig(), observed)
Model f_orig
├─ arguments (none)
├─ conditioned
│  └─ y => 1.0
└─ expressions
     x ~ Normal()
     y ~ Normal(x + 1)

Each key names a whole variable. For example, (y=[1.0, 2.0],) observes every y[i] ~ dist statement. Partial conditioning of an array or field is not supported. A missing entry does not make that entry latent. To mix observations and latent values, use separate variables or condition whole variables in a submodel.

Conditioning replaces the entire value of each supplied key. To remove conditioning, use decondition(cond_model, :y), or decondition(cond_model) to remove all conditioning. See Conditioning submodels for nested observations and deconditioning variables inside child models. Latent parameters remain VarNamedTuples, as described above.

Vectorisation

Wren models can be converted into a vectorised form, i.e., one where the parameters are supplied as a vector rather than a VarNamedTuple. This is done with the VecModel constructor, which takes a model and an AbstractADType object:

using Enzymevecmodel = VecModel(model, AutoEnzyme(; mode=Reverse))
VecModel f
├─ adtype => AutoEnzyme(mode=EnzymeCore.ReverseMode{false, false, false, EnzymeCore.FFIABI, false, false}())
├─ dimension => 4
├─ parameter space => UnconstrainedSpace()
└─ Model f
   ├─ arguments
   │  └─ y => 1.0
   ├─ conditioned (none)
   └─ expressions
        x ~ Normal()
        @observe(y ~ Normal(x + 1))
        z ~ MvNormal(zeros(3), I)
        return :hello

If you are only interested in vectorisation and not AD, you can pass nothing as the second argument:

noad_vecmodel = VecModel(model, nothing)
VecModel f
├─ adtype => nothing
├─ dimension => 4
├─ parameter space => UnconstrainedSpace()
└─ Model f
   ├─ arguments
   │  └─ y => 1.0
   ├─ conditioned (none)
   └─ expressions
        x ~ Normal()
        @observe(y ~ Normal(x + 1))
        z ~ MvNormal(zeros(3), I)
        return :hello

This is mostly useful when you want to handoff a Wren model to a different library which expects a vector interface. In particular, VecModels obey the LogDensityProblems.jl interface, and thus can be used with a wide range of other Julia packages that expect this.

You can draw a vectorised sample from a VecModel with vector_parameters:

v = vector_parameters(vecmodel)
4-element Vector{Float64}:
 -1.2542883749205342
  1.138009611047123
 -1.242346853113937
 -0.2996118881840605

or you can convert existing parameters into a vectorised form with vector_parameters:

ps = parameters(model)               # This is a VarNamedTuple in original model space.v = vector_parameters(vecmodel, ps)  # Convert it to vectorised (and unconstrained) form.
4-element Vector{Float64}:
 -1.9226026977925987
 -1.5313728063085115
 -0.6995759630486998
 -1.0726816341035845

Then you can calculate the log-density of these vectorised parameters, and their gradient:

import LogDensityProblems as LDPLDP.logdensity(vecmodel, v)               # Works without an adtype.LDP.logdensity_and_gradient(vecmodel, v)  # Requires an adtype.
(-10.283671343642672, [3.8452053955851975, 1.5313728063085115, 0.6995759630486998, 1.0726816341035845])
Note

If you have a use for higher-order derivatives like Hessians, please open an issue!

Wren in fact exports shorter functions for these, namely lp and lp_and_grad, which are directly equivalent to the above. Additionally, Wren provides an in-place gradient lp_and_grad! function, which may be useful for squeezing every last bit of performance out. LogDensityProblems.jl does not provide this (but if you have a good usecase for it, please consider adding a comment on this issue!).

None of these functions copy the parameter vector, so the model must not write into its latent variables; see the "Mutability" section of the syntax tutorial.

By default, VecModels are always run in UnconstrainedSpace(): that is, all parameters are transformed into a form where they can take any value in ℝ^n. The log-density calculation will then include the log-Jacobian term corresponding to this transformation. If this is not desired, you can specify a different parameter space, or a different log-density calculation function as a keyword argument to the VecModel constructor: please see its docstring for more info.

Warning

Vectorisation places certain restrictions on the structure of the model. In particular, it is not valid for a model to have a varying dimension. This can be caused either by parameters which have varying sizes, or models which simply have a varying number of parameters:

x ~ Poisson(3.0)y ~ MvNormal(zeros(x), I)  # dimension of `y` is not constantif x > 4    z ~ Normal()  # existence of `z` is not constantend

The set of variable names must also be constant across all model evaluations. Thus, even though the following model has a constant number of parameters, it is still not valid for vectorisation:

x ~ Normal()if x > 0    y ~ Normal()else    z ~ Normal()end
