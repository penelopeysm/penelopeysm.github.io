Defining models

On this page, we show how to define a probabilistic model with basic Wren syntax.

This page assumes that you know what a probabilistic model and its various components (e.g. parameters, observations) are. If you are not familiar with these concepts, you can read our introduction to probabilistic programming first.

Model bodies are functions

Wren allows you to define a probabilistic model as a function, but prefixed with the @wren macro:

using Wren, Wren.Dists@wren function my_model(m)    x ~ Normal(m)    return nothingend
my_model (generic function with 1 method)

The function body can be thought of as the probabilistic model itself: it provides a complete specification of how to perform forward simulation. Here, our forward simulation says: draw a random quantity x from a normal distribution centred at m, and then return nothing.

The body of a Wren model is plain Julia code, with some extra constructs that allow you to define probabilistic aspects of the model (which we'll explain later on this page). A corollary of this is that you can use almost any library inside a Wren model.

Function arguments are not special

If you have used Turing.jl before, you may know that arguments have a special meaning there in that they are observations (unless passed as missing).

This is not the case in Wren. In Wren, arguments have no special meaning: they are just quantities that can be used inside the model body.

Instantiating a model

To actually run this model, you will first have to create a Model struct, which can be thought of as Wren's own representation of a probabilistic model. To create one of these Models, you need to call the function, passing in any required arguments.

Calling a normal Julia function will run its body and give you its return value (here nothing). However, with the @wren macro, this is different: the function is rewritten such that calling it instead returns a Model object.

model = my_model(0.0)
Model my_model
├─ arguments
│  └─ m => 0.0
├─ conditioned (none)
└─ expressions
     x ~ Normal(m)
     return nothing

As we can see, this Model is a wrapper around its own arguments (here m = 0.0), plus the function body. (We'll come to conditioned later on this page.) At this point in time, the model itself has not been run at all. We will be able to do so by passing the newly created Model to all the APIs of Wren.

On this page, we'll demonstrate only one function for interacting with a Model, which is simulate. When given a Model object, this performs the forward simulation of the probabilistic model, returning a ModelResult struct that contains all the outputs we might be interested in.

simulate(model)
ModelResult
├─ parameters => VarNamedTuple
│  └─ x => -0.3850925759672498
├─ generated_quantities => VarNamedTuple()
├─ return_value => nothing
├─ logprior => -0.9930866792372188
└─ loglikelihood => 0.0

This includes the parameters, associated probabilities, as well as the original return value of the function body.

Random quantities

The most important custom syntax that Wren provides is the tilde operator (~). Much like the corresponding mathematical notation, x ~ dist means that x is a random quantity drawn from the distribution dist.

Left-hand sides

The left-hand side of a tilde can be either

  • a top-level variable, e.g., x ~ Normal(),
  • a field, e.g., m.x ~ Normal(),
  • an array element, e.g., a[1] ~ Normal(),
  • or chains thereof, e.g., m.a[1].x ~ Normal().

These are all things which can be assigned to in Julia (sometimes called 'lvalues'). Other expressions, including literals, are not (yet?) permitted.

Note that if you have a field or element on the left-hand side, the parent object must already exist. That is, you cannot write m[1] ~ Normal() or m.x ~ Normal() if m is not already defined.

Right-hand sides

Here, 'distributions' refer to any object that implements Base.rand(rng, dist) and DensityInterface.logdensityof(dist, x); the object doesn't have to subtype any abstract type. This includes those defined in Distributions.jl, as well as Wren's own distributions. Apart from distributions, it is also possible to put a Wren Model itself on the right-hand side of a tilde. In such a case, the Model is referred to as a submodel. Please see the submodels page for more information.

Parameters vs observations

Random quantities can be either parameters or observations. Parameters are the quantities that we want to infer, while observations are the quantities that we have observed in the real world.

By default, all x ~ dist statements are treated as parameters.

@wren function some_parameters(scalar, vector, nt)    scalar ~ Normal()    for i in eachindex(vector)        vector[i] ~ Normal()    end    nt.a ~ Normal()    return nothingendsimulate(some_parameters(0.0, zeros(3), (; a=0.0)))

Notice here how all of scalar, vector[i], and nt.a appear as 'parameters' in the ModelResult. It doesn't matter that they were passed in as arguments.

There are two ways to turn a random quantity into an observation:

  1. Marking the tilde with @observe:
@wren function observations(y)    x ~ Normal()    @observe y ~ Normal(x)endsimulate(observations(1.0))
ModelResult
├─ parameters => VarNamedTuple
│  └─ x => -0.110485827477063
├─ generated_quantities => VarNamedTuple()
├─ return_value => 1.0
├─ logprior => -0.9250420922413184
└─ loglikelihood => -1.5355279197183815

  1. Conditioning the model on a value. First, you need to instantiate the unconditioned model; then, you can condition it using the | operator, passing in a NamedTuple of observations.

    Conditioning on y actually does two things: firstly, it marks the corresponding random quantity as an observation, and secondly, it sets the value of that random quantity to the value you passed in. Notice that @info y works here and uses the value of y that the model was conditioned on.

@wren function observations()    @info y    x ~ Normal()    y ~ Normal(x)endconditioned_model = observations() | (; y=1.0)
Model observations
├─ arguments (none)
├─ conditioned
│  └─ y => 1.0
└─ expressions

     x ~ Normal()

In general, conditioning is more flexible as you can 'recover' the original model by calling decondition:

original_model = decondition(conditioned_model)simulate(original_model)

├─ parameters => VarNamedTuple
│  ├─ x => 1.2736765317049985
│  └─ y => 0.36187407224747314
├─ generated_quantities => VarNamedTuple()
├─ return_value => 0.36187407224747314
├─ logprior => -3.0646948826537788

However, if you don't need this functionality, @observe can be more explicit. @observe can also be used if you want to calculate the log-likelihood of some quantity that is calculated inside the model body, rather than being passed in as an argument.

Special nodes

The above should be enough to get you started with defining models in Wren. However, there are also some special nodes that you can use in your model body.

@iid and @batch

In the common case where you have an array of parameters that share the same distribution, you can use these macros, which have the same semantics as a naive for-loop but can have optimised performance.

@iid is used for independent and identically distributed random quantities, i.e., each element of the array is drawn independently from the same distribution. You can either pass in an existing array, or if you want to create a new array, you can specify how many elements there are with the size keyword argument.

@wren function with_iid(existing_array, n)    @iid new_array ~ Normal() size=n    @iid existing_array ~ Normal()end
with_iid (generic function with 1 method)

@batch is intended to be applied to for-loops, and attempts to vectorise the loop body where safe. The following has exactly the same semantics as the version without @batch, but may be faster (depending on various factors).

@wren function with_batch(x, y)    @batch for i in eachindex(x)        x[i] ~ Normal()        @observe y[i] ~ Normal(x[i])    endend
with_batch (generic function with 1 method)

It's worth pointing out here that @batch is not 'magical': it works only with a restricted set of syntax and is not guaranteed to be faster than a naive for-loop. It is often worth benchmarking your model if you want to optimise performance.

@gq

Inside a model body, you may have other quantities of interest that you want to extract, even if they are not parameters. You can mark these quantities with the @gq macro.

Subject to rename

It is likely that this macro will be renamed in the very near future.

By default, simulate will return these quantities:

@wren function with_gq()    x ~ Normal()    @gq x_sq = x^2    y ~ Normal(x)endmodel = with_gq() | (; y=1.0)simulate(model)

@addloglikelihood

This manually increments the log-likelihood of the model. For example, the following is equivalent to @observe y ~ Normal(x) if y is 1.0 (albeit rather less clear).

@wren function with_addloglikelihood()    x ~ Normal()    @addloglikelihood logdensityof(Normal(x), 1.0)endsimulate(with_addloglikelihood())

Technical restrictions

Although Wren models can contain almost completely arbitrary Julia code, due to some technical limitations of RuntimeGeneratedFunctions.jl, certain constructs are not allowed in Wren models.

The biggest one of these is that Wren models cannot close over local variables, or in other words, your model cannot use local variables defined outside the model body.

For example:

julia> for d in [Normal()]           # d is a local variable here.                  @wren function closes_over_local()               # ... but our model uses it               x ~ d           end                  simulate(closes_over_local())       endERROR: UndefVarError: `d` not defined in `Main`Suggestion: check for spelling errors or missing imports.

The easiest way around this is to pass the variable into the model as an argument:

res = Any[]for d in [Normal()]    @wren function passes_local_in(d)        x ~ d # OK since d is an argument.    end    push!(res, simulate(passes_local_in(d)))endonly(res)
ModelResult
├─ parameters => VarNamedTuple
│  └─ x => 1.4653868955379261
├─ generated_quantities => VarNamedTuple()
├─ return_value => 1.4653868955379261
├─ logprior => -1.992617910011813
└─ loglikelihood => 0.0

Closing over global variables is fine (although in general we recommend avoiding global variables; it's cleaner to pass things you need into the model as arguments).

Another rather niche restriction is that Wren models cannot contain macros that create closures. The most likely situation where you would run into this is if you are using Reactant.@trace; please see the Working with Reactant page for more information.
