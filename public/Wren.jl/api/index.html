Wren.AbstractAccumulator — Type
AbstractAccumulator

An abstract type for accumulators.

An accumulator is an object that may change its value at every tilde_assume!! or tilde_observe!! call based on the random variable in question. The obvious examples of accumulators are the log prior and log likelihood. Other examples might be a variable that counts the number of observations in a trace, or a list of the names of random variables seen so far.

An accumulator type T <: AbstractAccumulator must implement the following methods:

  • accumulator_name(acc::T) or accumulator_name(::Type{T})
  • accumulate_observe!!(acc::T, val, vn, dist, template, sitename)
  • accumulate_assume!!(acc::T, val, tval, vn, dist, logjac, template, sitename)
  • reset(acc::T)
  • Base.copy(acc::T)

In these functions:

  • val is the new value of the random variable supplied by a latent source (always in the distribution's original space), or the value on the left-hand side of an observe statement.
  • tval is the TransformedValue produced by interpreting the value supplied by the latent source in the selected parameter space.
  • dist is the distribution on the RHS of the tilde statement.
  • logjac is the forward log absolute determinant of the Jacobian for the transform from the distribution's original space to the representation selected by the parameter space.
  • vn is the VarName that is on the left-hand side of the tilde-statement. If the tilde-statement is a literal observation like 0.0 ~ Normal(), then vn is nothing.
  • template is a value that conveys the shape of the top-level symbol in vn, and is used specifically for accumulators that carry VarNamedTuples.
  • sitename is a compile-time Symbol identifying the sampling site in the model source code. Each distinct tilde statement has a unique sitename.

To be able to work with multi-threading, it should also implement:

  • split(acc::T)
  • combine(acc::T, acc2::T)

See the documentation for each of these functions for more details.

Wren.AbstractLatentSource — Type
AbstractLatentSource

An abstract type representing somewhere from which the values of latent variables can be obtained.

Wren provides several subtypes of AbstractLatentSource:

  • FromPrior: samples latent variables from their prior distributions
  • FromParams: provides latent variables in a VarNamedTuple
  • FromVector: provides a vector of flattened latent variables, together with information about how to convert them back into the original space

Custom subtypes of this can be created to customise model execution. To be a valid AbstractLatentSource, a type must implement

  • get_latent(source, vn, dist) to obtain a latent variable from the source, and
  • scope to obtain a latent source that applies only to a subset of variables. This is used in submodel evaluation: if a model contains a ~ submodel(), then the latent source used to evaluate submodel is obtained by calling scope(source, @vn(a)).

Wren.AbstractParameterSpace — Type
AbstractParameterSpace

The coordinate space in which latent parameters and their density are represented.

An AbstractParameterSpace can be thought of as a collection of AbstractTransforms, one for each latent variable in a model. However, while AbstractTransforms represent information that has already been decided (i.e., it is irrevocably tied to the value stored in a TransformedValue), an AbstractParameterSpace more resembles an upfront specification of how one wants to evaluate a model.

When evaluating a model with a given AbstractParameterSpace, the model's latent variables will be transformed into the representation that it specifies (using target_transform). The log-Jacobian that is accumulated, and hence the log-density, will be with respect to the coordinate space specified by the AbstractParameterSpace.

There are two built-in AbstractParameterSpaces:

  • UnconstrainedSpace: all latent variables are represented in unconstrained, vectorised space. This is the default for Wren's vectorised models, particularly because this is most suitable for gradient-based inference methods and automatic differentiation.

  • OriginalSpace: all latent variables are represented in their original space.

This can be extended in future to support FixedTransforms.

Wren.AccumulatorTuple — Type
AccumulatorTuple{N,T<:NamedTuple}

A collection of accumulators, stored as a NamedTuple of length N

This is defined as a separate type to be able to dispatch on it cleanly and without method ambiguities or conflicts with other NamedTuple types. We also use this type to enforce the constraint that the name in the tuple for each accumulator acc must be accumulator_name(acc), and these names must be unique.

The constructor can be called with a tuple or a VarArgs of AbstractAccumulators. The names will be generated automatically. One can also call the constructor with a NamedTuple but the names in the argument will be discarded in favour of the generated ones.

Wren.LogJacobianAccumulator — Type
LogJacobianAccumulator{T<:Number} <: LogProbAccumulator{T}

An accumulator that tracks the cumulative forward log absolute determinant of the Jacobian from the distribution's original space to the representation selected by the parameter space.

Note

With OriginalSpace, the log-Jacobian is zero. With UnconstrainedSpace, it is the forward log-Jacobian from original space to unconstrained vector space.

In general, for the forward Jacobian $\mathbf{J}$ corresponding to the function $\mathbf{y} = f(\mathbf{x})$,

\[\log(q(\mathbf{y})) = \log(p(\mathbf{x})) - \log (|\mathbf{J}|)\]

and correspondingly:

logjoint_transformed(accs) = logjoint(accs) - logjac(accs)

Fields

  • logjac::Number: the forward log absolute determinant of the selected transform Jacobian

Wren.LogProbAccumulator — Type
LogProbAccumulator{T} <: AbstractAccumulator

An abstract type for accumulators that hold a single scalar log probability value.

Every subtype of LogProbAccumulator must implement

  • A method for logp that returns the scalar log probability value that defines it.
  • A single-argument constructor that takes a logp value.
  • accumulator_name, accumulate_assume!!, and accumulate_observe!! methods like any other accumulator.

LogProbAccumulator provides implementations for other common functions, like convenience constructors, copy, show, ==, isequal, hash, split, and combine.

This type has no great conceptual significance, it just reduces code duplication between types like LogPriorAccumulator, LogJacobianAccumulator, and LogLikelihoodAccumulator.

Wren.LogProbType — Type
LogProbType

The default type used for log-probabilities in Wren.jl. This is a compile-time constant that can be set via set_logprob_type!, which under the hood uses Preferences.jl.

Note that this does not prevent computations within the model from promoting the log-probability to a different type. In essence, LogProbType specifies the lowest possible type that log-probabilities can be, and Wren promises to not insert any extra operations that would cause this to be promoted to a higher type. However, Wren cannot guard against user code inside models.

For example, in:

@wren f() = x ~ Normal(0.0, 1.0)

the log-probability of the model will always be promoted to Float64, regardless of the value of LogProbType, because the logpdf of Normal(0.0, 1.0) is a Float64. On the other hand, in:

@wren f() = x ~ Normal(0.0f0, 1.0f0)

the log-probability of the model will be Float32 if LogProbType is Float32 or lower.

Wren.NoLogProb — Type
NoLogProb <: Real

Singleton type that represents the absence of a log probability value. This is used as the default type parameter for LogProbAccumulator when no log probability value is needed, to avoid defining a concrete type such as Float64 that would cause unwanted type promotion when accumulating log probabilities of other types (e.g., Float32).

Adding anything to NoLogProb() returns the other thing. In other words, NoLogProb is a true additive identity which additionally preserves types.

Wren.RangesAndTransforms — Type
RangesAndTransforms

Holds a VarNamedTuple mapping VarName => RangeAndTransform, together with a fast-path NamedTuple mapping sitename => RangeAndTransform.

The inner constructor takes a VarNamedTuple and a mapping of sitename => VarName pairs. This guarantees that the actual information stored in both fields are consistent.

When evaluating a model with FromVector, Wren first checks the sitename_lookup to see if the RangeAndTransform has been stored there. If it hasn't, then it will do the potentially slower VarNamedTuple lookup.

The fast path is only hit for sampling sites that are encountered once and only once during model evaluation. This allows us to completely elide VarNamedTuple lookups for these sites. Usually that's not a problem, but VarNames like x[1:100000] can be very slow due to PartialArray and ArrayLikeBlock checks.

The implicit assumption here is that if sitename was only encountered once during the construction of the RangesAndTransforms, then it will only be encountered once during every model evaluation. This is true of essentially any model that is amenable to vectorisation.

An interesting case to ponder is a model like this. In the absence of this fast path (i.e., if there was only VNT-based lookup like DynamicPPL), this is compatible with vectorisation as long as dist1 and dist2 have the same Plaice.unconstrained_vec_size, because the resulting RangeAndTransform will be a constant:

if something    x ~ dist1else    x ~ dist2end

With the fast path, it's quite possible that the sitename for the if branch will be stored, and the sitename for the else branch won't. This means that during model evaluation, the fast path will only work if we hit the same branch. However, even if we hit the other branch, the slow path will still work (because x's RangeAndTransform will still be stored in the VNT!)

Wren.SiteNameTracker — Type
SiteNameTracker

Accumulator that identifies sampling sites hit exactly once during model evaluation. On the first hit of a sitename, its VarName is stored in a NamedTuple keyed by sitename. On any subsequent hit, the entry is removed and the sitename is blacklisted so it is never re-added.

After evaluation, entries contains only the single-hit sites, mapping sitename => VarName. This is used to build a fast NamedTuple lookup for ranges and transforms, bypassing the slower VarNamedTuple path.

Wren.VNTAccumulator — Type
VNTAccumulator{AccName}(f::F, values::VarNamedTuple=VarNamedTuple()) where {AccName,F}

A generic accumulator that applies a function f to values seen during model execution and stores the results in a VarNamedTuple.

AccName is the name of the accumulator, and is exposed to allow users to define and use multiple forms of VNTAccumulator within the same set of accumulators. In theory, each VNTAccumulator with the same function f should use the same accumulator name. This is not enforced.

The function f should have the signature:

f(val, tval, vn, dist, logjac) -> value_to_store

where the arguments have their usual meanings in accumulate_assume!!. If a value does not need to be accumulated, this can be signalled by returning DoNotAccumulate() from f.

If f is a struct (and not a function), you also need to define Base.copy on f.

Wren.VecModel — Type
VecModel(
    model::Model,
    adtype::Union{ADTypes.AbstractADType,Nothing};
    lp_function=logjoint_transformed,
    params=FromPrior(),
    parameter_space=UnconstrainedSpace()
)

A vectorised form of model, which is designed to take a single vector of parameters as input, and returns a scalar log-density.

Overview

This is accomplished by storing the original model, together with a set of ranges and transforms which map segments of the parameter vector to the latent variables' values in original space. For example, consider

@wren function my_model()    x ~ Normal()    y ~ Normal()end

The mapping from params, a vector of length 2 to the latent variables takes the form:

x_info = mapping[@vn(x)] # This is a `RangeAndTransform` object.x = x_info.transform(params[x_info.range])y_info = mapping[@vn(y)]y = y_info.transform(params[y_info.range])

where x_info.range might be 1:1 and y_info.range might be 2:2.

In order for this to work reliably, the model must have a fixed set of latent variables and fixed dimension. If these conditions are not adhered to, it is very likely that results obtained will be meaningless. Models with varying parameter order can be safely vectorised since the mapping is invariant to the order in which the latent variables are encountered.

Positional arguments

  • model::Model: The model to vectorise.

  • adtype::Union{ADTypes.AbstractADType,Nothing}: The automatic differentiation backend to use for gradient calculations. You can pass nothing to construct a log-density-only model that is not capable of computing gradients.

    In Wren, we recommend using reverse-mode Enzyme as the default backend as that offers the most performance. This can be specified with AutoEnzyme(; mode=Reverse) (these identifiers are re-exported by Wren).

    However, in some cases you may find that Enzyme errors. In such a case, please do open an issue: we want to help fix this! In such cases you can use a different AD backend. Wren is backed by DifferentiationInterface.jl so you can plug in any AbstractADType.

Keyword arguments

  • params::AbstractLatentSource: when preparing a VecModel, Wren requires information about the model's latent variables in order to construct the mapping from vector to latent variables. This can most easily be obtained by running the model once with an AbstractLatentSource, which you can pass here. If you want to control the RNG with which these parameters are drawn, you can use FromPrior(rng).

    If you have already run the model once, you can avoid reevaluation by directly passing the requisite information. This is mostly intended for advanced usage, please see the Wren source code for examples of how to do this.

  • lp_function: When the model is evaluated, it will return a set of accumulators, which must then be collapsed into a single scalar log-density. This function is responsible for that (i.e., it must have the signature f(accs::AccumulatorTuple) -> Number). The default is logjoint_transformed, which evaluates the log joint density in transformed space. This is virtually always what you want, but you can also use logprior, loglikelihood, or logjoint, or write your own.

  • parameter_space::AbstractParameterSpace: The parameter space in which the vectorised model is defined. The default is UnconstrainedSpace, which is almost always what you want (again this is mostly for compatibility with gradient-based inference algorithms).

Wren.apply_parameter_space — Method
apply_parameter_space(
    parameter_space::AbstractParameterSpace,
    tval::TransformedValue,
    vn::VarName,
    dist,
)

Convert a latent value into the representation specified by parameter_space.

Given a parameter_space which says how a latent variable should be represented, and a TransformedValue which contains a value and its current representation (derived from the AbstractLatentSource), returns a tuple of:

  • the value in original model space,
  • the value in the target representation (a TransformedValue), and
  • the forward log absolute determinant of the Jacobian from original space to the target representation.

Note that when evaluating a model, even if the values are already supplied in unconstrained space and the target representation is also unconstrained, we still have to perform the inverse transform to original space for two reasons:

  • Calculation of the log-Jacobian.
  • The left-hand side of the tilde-statement contains a variable, and we must assign the value in original space to that variable.

Wren.benchmark_and_test — Method
benchmark_and_test(
    model::Wren.Model,
    adtype::Union{Nothing,DI.AbstractADType};
    kwargs...
) -> ModelRunResult

Test and benchmark a model, optionally including its vectorised form and AD.

Note that if adtype is specified, the corresponding backend package must be loaded first.

This function evaluates performance at multiple levels:

  • Model level: benchmarks rand (sampling from the prior) and logjoint (log-joint density evaluation).
  • VecModel level: benchmarks lp (log-density of the vectorised model) and lp_and_grad (log-density and its gradient).

If test_correctness is also specified, then the log-density and gradient returned by the AD backend are compared against either a reference backend or a manually specified expected result.

Keyword arguments

The lp_function and parameter_space keywords are forwarded to VecModel, and have the same defaults.

Wren.evaluate — Method
evaluate(model, latent_source, parameter_space, accs)

Evaluate model in three stages for every latent variable:

  1. latent_source supplies a TransformedValue.
  2. parameter_space determines the model-space value, target representation, and forward log-Jacobian.
  3. accs accumulate the resulting information.

All three components are required. Higher-level interfaces may choose defaults, but this method keeps the evaluation pipeline explicit.

Wren.logjac — Method
logjac(accs::AccumulatorTuple)::Number

Return the accumulated log-absolute determinant of the Jacobian of the transformation from original to the space that the model was evaluated in. If the model is evaluated in original space, this will be zero. However, if the model was evaluated in transformed space, then this is J_f(x) where f is the forward transformation into the evaluation space.

Consequently, the log-joint density in transformed space is given by

logjoint_transformed(accs) = logjoint(accs) - logjac(accs)

(note the minus sign).

Wren.scope — Function
scope(source::AbstractLatentSource, vn::VarName) -> AbstractLatentSource

Restrict source such that it only provides values for sub-variables of vn. This is used when evaluating submodels with a prefix vn.

This is best explained through an example. Suppose you have a model with

@wren function inner()    x ~ Normal(0, 1)end@wren function outer()    a ~ inner()end

When evaluating outer, the latent source may contain a value for the variable a.x. For example, you might have FromParams(VarNamedTuple(a=VarNamedTuple(x=1.0))). However, when evaluating inner, the submodel does not know about the prefix a: Wren will call scope to obtain a subsetted latent source which only contains the variable x.

Wren.set_logprob_type! — Method
set_logprob_type!(::Type{T}) where {T}

Set the log probability type for Wren.jl, Wren.LogProbType, to T. Permitted values are Float64, Float32, Float16, and NoLogProb. The default in Wren is Float64.

NoLogProb is a special type that is the "lowest" possible float type. This means that the log probability will be promoted to whatever type the model dictates. This is a totally unintrusive option, which can be useful if you do not know in advance what log probability type you are targeting, or want to troubleshoot a model to see what type the log probability is being promoted to. However, this can also cause type stability issues and performance degradations, so we generally recommend setting a specific log probability type if you know what type you want to target.

This function uses Preferences.jl to set a compile-time constant, so you will need to restart your Julia session for the change to take effect.
