Working with Reactant

Reactant.jl is a Julia package which compiles Julia code into lower-level representations (MLIR and XLA) that can be run on accelerators like GPUs, often with very significant speedups.

One of the core design goals of Wren is to be maximally compatible with Reactant. We acknowledge that this can be difficult: Reactant itself is a very ambitious project, and still has some rough edges. Furthermore, Wren models can contain almost arbitrary code, and in general it is not Wren's responsibility to ensure that all of this code is compatible with Reactant.

However, at the same time, we strongly believe that this will help to push the Julia ecosystem forward and make Reactant work better for everybody. To this end, we ask you to please report any issues you encounter when using Wren with Reactant. We can help to minimise issues, file them upstream, and in some cases even fix them.

Distributions

Before we even begin to talk about models, we should note that Reactant will run into many problems with Distributions.jl. There are many reasons for this, but the main one is that Reactant's tracing mechanism requires that functions accept subtypes of Number, and virtually all functions in Distributions require Real arguments.

The creation of the Wren.Dists module was almost completely motivated by this. To make Wren models compatible with Reactant, we recommend that you use Wren's built-in distributions as far as possible. If there isn't a distribution you need, do feel free to open an issue or a pull request!

Using Reactant with Wren

Currently, Reactant can only be used with vectorised Wren models, i.e., the VecModel struct. Because this struct obeys the LogDensityProblems.jl interface, this does still allow for compatibility with a wide range of packages that expect this interface! In particular, you can use Reactant with Wren's nuts sampler (which uses DynamicHMC under the hood).

To enable Reactant, you have to pass AutoReactant{<:AutoEnzyme} as the second argument to VecModel (i.e., as the AbstractADType argument). Let's define our eight-schools model yet again, but this time with Reactant enabled:

using Wren, Wren.Dists, Reactanty = [28, 8, -3, 7, -1, 1, 18, 12]sigma = [15, 10, 16, 11, 9, 11, 10, 18]J = 8@wren function eight_schools(y, sigma, J)    mu ~ Normal(0, 5)    tau ~ HalfCauchy(0, 5)    theta ~ MvNormalScale(fill(mu, J), tau * I)    @batch for i in 1:J        @observe y[i] ~ Normal(theta[i], sigma[i])    end    return (mu=mu, tau=tau)endmodel = eight_schools(y, sigma, J)vm = VecModel(model, AutoReactant(DEFAULT_AD))

Host / device transfer

While the implementation of Reactant acceleration above works, it is in fact extremely naive.

Reactant works by compiling the model evaluation function into XLA code which is then executed on a device (such as a GPU; or if you are running this locally, maybe a different part of your CPU). However, before it can execute this code, it has to transfer the input arguments from the host (your CPU) to the device. Furthermore, once it has finished evaluating this model, it has to transfer the results back from the device to the host.

The implementation of lp and lp_and_grad above encompasses all of these steps (i.e., lp takes a host array, transfers it to the device, evaluates the model on the device, and then transfers the float result back to the host). This transfer can be quite expensive, and can easily dominate the time taken to evaluate a small model. Eight-schools firmly falls into the small-model category:

This means that in Wren's current state, Reactant is likely to be most useful for large models, such as those with large datasets / likelihood terms, where the fixed cost of transferring the data is small in comparison to the cost of evaluating the model.

It should be emphasised that this is not a fundamental limitation of Reactant. Instead, it is a choice that is made in Wren in order to abstract away these details of host/device transfer from the user. We would very much like to change this in the future, and allow VecModel to use device arrays as inputs and outputs. The difficulty with this is that everything else that the VecModel slots into, such as a HMC or NUTS sampler, needs to be converted into a form that is also compatible with Reactant. At present, to the best of our knowledge, we don't really have that available to us.

(Conceptually, what we would like to have is something like the 'iterative NUTS' procedure developed for NumPyro. That is more or less the same thing as having a Reactant-compatible NUTS sampler, but for JAX instead of Reactant.)

Do I need to call to_rarray?

When invoking Reactant outside of Wren you may be aware that you often need to call Reactant.to_rarray on input arguments so that they are 'tracked' by the Reactant compiler. Wren handles this for you by unconditionally calling to_rarray on all input arguments to the model, so you do not need to worry about this.

Semantically, this is not the right thing to do: if you have an argument which is constant (i.e., you never want to evaluate the model with a different value of that argument), then we should not call to_rarray on it, as that causes extra work for Reactant. Model arguments should in theory always fall into this category, since once the model has been created, the arguments can't be changed without creating a new model!

Unfortunately, at the present moment there are a handful of issues which cause Reactant to grind to a halt when performing matrix multiplications with untraced arrays. (See the WrenCore source code for more details.) It is our hope that these can be fixed soon, which will allow us to remove this unconditional to_rarray call and potentially improve performance.

Reactant's @trace macro

Users of Reactant may be familiar with @traced for loops or conditionals.

Unfortunately, one current restriction of Wren is that you cannot use @trace inside a Wren model.

The reason for this is incredibly technical. As described in the compilation model, Wren uses RuntimeGeneratedFunctions.jl to create the model evaluation function. RGF, or specifically its @RuntimeGeneratedFunction macro, must be able to 'see' the closure in order to convert it to a Julia opaque closure. However, Wren does not expand macros in the body before passing it to @RuntimeGeneratedFunctions.

It's very possible that this can be fixed: apparently, Claude managed to do it, so a human just has to get round to checking it.
