Staged computation

One of Wren's unique features is that it uses staged computation to generate the evaluation functions for models. That sounds like a scary term, but it essentially means that the evaluation function is not generated in a single shot but rather in a multi-stage pipeline:

flowchart TD A[Model definition] --> B[Probabilistic intermediate representation] B --> C[Evaluation function]

The model definition is what you write:

using Wren, Wren.Dists@wren function my_model(y)    x ~ Normal()    @observe y ~ Normal(x)endmodel = my_model(1.0)
Model my_model
├─ arguments
│  └─ y => 1.0
├─ conditioned (none)
└─ expressions
     x ~ Normal()
     @observe(y ~ Normal(x))

The probabilistic IR looks something like the following, but a bit more complicated:

[Sample(:x, :(Normal())), Observe(:y, :(Normal(:x)))]
The actual IR

And the evaluation function is conceptually something like

function __mymodel_evaluate__(y, params, accs, ...)    x = rand(Normal())    lp_x = logdensityof(Normal(), x)    accs = add_logprior(accs, lp_x)    lp_y = logdensityof(Normal(x), y)    accs = add_loglikelihood(accs, lp_y)    return accsend

Why do this?

This pipeline does seem complicated. In particular, one might ask why we don't just generate the evaluation function directly from the model definition. (Indeed, a macro would do this quite easily, and that's more or less how DynamicPPL works, for example.)

The main motivation is that the intermediate representation (IR):

  • gives Wren some information about the model which it can use to (more efficiently) generate the evaluation function;
  • allows Wren to do some optimisations, for example elision of submodel parameter collection;
  • allows for the programmatic generation of Wren models, in that a user can construct an IR and then generate a Wren model from it, instead of having to do some macro gymnastics to create the original model definition.

This of course doesn't come for free. Besides the substantial extra complexity of the codebase, it also means that we have to use RuntimeGeneratedFunctions.jl in the second step (IR to evaluation function), which brings with it some limitations. For example, model bodies cannot close over local variables (only global variables). This is surprisingly easy to trigger:

julia> for d in (Normal(), Exponential())           # d is a local variable...                  @wren function oops_closed_over_local()               # ... but our model closes over it               x ~ d           end                  model = oops_closed_over_local()           rand(model)       endERROR: UndefVarError: `d` not defined in `Main`Suggestion: check for spelling errors or missing imports.

This can be worked around, for example by passing d into the model as an argument. However, it's still of course a limitation, and the error message isn't super helpful either.

IR and syntax design

Above we saw two of the 'special expressions' that Wren uses in its IR, namely Sample and Observe. These have a very unimaginative one-to-one mapping to the special nodes in Wren:

SyntaxIR node
a ~ bSample
@observe a ~ bObserve
@iid size=N ...IID
@batch for ...Batch
@addloglikelihood ...AddLogLikelihood
return ...ReturnStatement

As you can see, most of these are denoted by macros. As it turns out, none of these macros actually have a meaning outside of Wren model bodies: they don't actually expand into anything. They simply serve as syntax markers for the IR generation stage.

Why macros, though? To begin with, we are fundamentally limited by Julia syntax: we can't invent our own syntax, because it has to be parsed by a normal Julia macro (@wren). So we can't, for example, write [observe] a ~ b as that simply won't parse.

Then, we don't want to hijack any preexisting Julia syntax. This means that, for example, we don't want to parse a => b into something, because that usually means Pair(a, b) in Julia. Once we eliminate those, we are actually left with very few operators that aren't weird Unicode stuff that is impossible to type.

In principle, we could use any kind of function call to denote these. For example, we could say that sample(a, b) is what is now a ~ b, and iid(sample(a, b); size=N) is what is now @iid size=N a ~ b. However, this is a bit too understated: it looks just like a normal function call, and it's not obvious to the user that these have special semantics.

Macros are the best compromise between all of these. We aren't restricted to a fixed set of possibilities (as is the case with operators), but also to most Julia programmers it should be intuitive that macros have special effects!

Programmatic generation

The above claim that the IR allows for programmatic generation is very carefully worded: there is no meaningful API for this yet.

However, you can in principle do something like this:

using WrenCore.Expressions: Sample, Observe, AbstractWrenExprusing WrenCore: RuntimeGeneratedFunctionsstmts = AbstractWrenExpr[    Sample(:sample_x, :x, Normal(), :x, true),    Observe(:observe_y, :y, :(Normal(x))),]RuntimeGeneratedFunctions.init(@__MODULE__)manual_model = Wren.Model(:my_model, (; y=1.0), stmts, @__MODULE__)
Model my_model
├─ arguments
│  └─ y => 1.0
├─ conditioned (none)
└─ expressions
     x ~ Normal{Float64, Float64}(0.0, 1.0)
     @observe(y ~ Normal(x))

Obviously, this leaks internal details of Wren, and is not exactly a user-friendly API. However, it does show that it should be possible to construct the stmts array programmatically, generate a Wren model from it, and then use that model:
