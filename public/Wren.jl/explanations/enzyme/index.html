Working with Enzyme

The Julia ecosystem has had (infamously) a number of automatic differentiation packages, each with their own tradeoffs. Wren adopts a partly opinionated approach to AD. All (sensible) AD backends are supported via DifferentiationInterface.jl, so the user can choose their preferred backend. However, at the same time, Wren also tries very hard to make it possible for you to use reverse-mode Enzyme as the backend.

The developer(s) of Wren are not affiliated with any AD backend and this opinion is not rooted in any politics or personal disagreement. It is purely based on the fact that reverse Enzyme is the fastest AD backend across a wide range of problems (see, e.g., the benchmarks on Turing.jl). Thus, we consider it a disservice to choose any other backend as the default, as that simply leaves performance on the table.

At the same time, we recognise that Enzyme can be difficult to use and still has a number of edge cases. Wren does its best to make this experience as seamless as possible for users. However, it is greatly appreciated if you help us by reporting cases where Enzyme fails to work. We can (usually) help with minimising bugs and filing issues upstream, which will not only help you but also everyone else who uses Enzyme!

Runtime activity

Wren does not generally require you to enable runtime activity when using Enzyme. Thus, you can simply use DEFAULT_AD (an alias for AutoEnzyme(; mode=Reverse)) as the adtype when e.g. sampling with NUTS, or constructing a VecModel.

However, depending on how the model is written, sometimes Enzyme detects that it is necessary to use runtime activity. If you are familiar with Enzyme, you will know that this usually causes an error to be thrown. However, Wren will, by default, detect such situations and automatically enable runtime activity for you. Note that even with runtime activity enabled, Enzyme still tends to be the fastest AD backend, so you do not really need to be concerned about this.

This behaviour can be controlled via the function WrenCore.set_auto_runtime_activity!:

WrenCore.set_auto_runtime_activity! — Function
WrenCore.set_auto_runtime_activity!(val::Union{Bool,Nothing})

Set Wren's automatic runtime activity behaviour.

When using Enzyme as the AD backend, depending on how the model is constructed, it may be necessary to enable runtime activity. This can often allow more expressive models to be differentiated, but comes at a performance cost.

Wren recommends using reverse-mode Enzyme, i.e., AutoEnzyme(; mode=Reverse) as the AD backend, which does not enable runtime activity. By default, Wren will automatically enable runtime activity if Enzyme requires it.

If you would rather have Wren raise an error, set

WrenCore.set_auto_runtime_activity!(false)

Or if you want an info message instead of an error, set

WrenCore.set_auto_runtime_activity!(nothing)

To restore the default behaviour (silently enabling runtime activity), set

WrenCore.set_auto_runtime_activity!(true)

When exactly is runtime activity required?

The easiest way to trigger a need for runtime activity is to bundle differentiable and non-differentiable data into the same struct. Often there is not much you can do as a user to avoid this situation, which is precisely why Wren intentionally catches the error for you.

Differentiable data, in the context of Wren, refers to the actual parameters of the model (i.e., the things we want to know gradients with respect to). For example, if you have x ~ MvNormal(...), then x contains differentiable data during model evaluation. Non-differentiable data usually means constants that are supplied to the model.

Consider, for example, the following model:

using Wren, Wren.Dists, Enzyme@wren function f_rta(sigma, y)    m ~ MvNormalScale(zeros(4), I)    y ~ MvNormalScale(m, Diagonal(sigma))end
f_rta (generic function with 1 method)

Here, m is differentiable data, whereas sigma is non-differentiable data. Mixing these two things in the same struct (i.e., MvNormalScale) will trigger Enzyme's runtime activity requirement.

However, at the same time, it's clearly not possible to rewrite the model to avoid this. If the offending struct is only used as an observation distribution, then you can manually write out the log-likelihood and use @addloglikelihood and thus avoid making the struct, but this is less expressive and will make your model less usable.

Avoiding runtime activity by copying

The need for runtime activity in the above case can also be overcome by creating a copy of sigma inside the model.

@wren function f_copy(sigma, y)    m ~ MvNormalScale(zeros(4), I)    y ~ MvNormalScale(m, Diagonal(copy(sigma)))end
f_copy (generic function with 1 method)

We can prove that this doesn't need runtime activity by setting WrenCore.set_auto_runtime_activity!(false) (which will error if runtime activity is required):

In this case we can see that using the copy slows things down. In general, the cost of copies will scale with the size of the arguments and can in principle get very large, whereas runtime activity roughly scales with the number of pointer operations that Enzyme is doing. Furthermore, eliding copies also makes the primal faster (as seen above), and also reduces GC pressure.

Copying model arguments on evaluation

Wren sometimes copies model arguments when evaluating models with Enzyme.

Why do we need copies?

When originally written, Wren would never copy any model arguments during model evaluation (it would copy them when creating the model, but not when evaluating it, since the latter is usually done many more times).

This very simple rule had to (sadly) be changed because it could silently cause incorrect results with Enzyme. Specifically, this could happen if differentiable data was written into a model argument, and then read out again.

Consider the following model, which is only slightly modified from the previous section's to get rid of sigma:

using Wren, Wren.Dists, Enzyme@wren function no_sigma(m, y)    m[1:4] ~ MvNormalScale(zeros(4), I)    @observe y[1:4] ~ MvNormalScale(m[1:4], I)end
no_sigma (generic function with 1 method)

The astute reader will notice that this is actually a batched for-loop in disguise:

@wren function batched(m, y)    @batch for i in eachindex(y)        m[i] ~ Normal(0, 1)        @observe y[i] ~ Normal(m[i], 1)    endendmodel = batched(randn(4), randn(4))
Model batched
├─ arguments
│  ├─ m => [-1.00242, 0.12334, -0.287165, 1.47189]
│  └─ y => [1.75611, 2.03169, 0.230426, 0.159259]
├─ conditioned (none)
└─ expressions
     @batch(name = Symbol("##batch#28712"), for i = eachindex(y)
             m[i] ~ Normal(0, 1)
             @observe y[i] ~ Normal(m[i], 1)
         end)

Anyway, Wren emits a model evaluation function that conceptually looks like:

function batched_eval(params, m, y)    lp = 0.0    m[1:4] = params[1:4]    lp += logpdf(MvNormal(zeros(4), I), m[1:4])    lp += logpdf(MvNormal(m[1:4], I), y[1:4])    return lpend

Notice that here params is differentiable, but m and y are not. Wren marks the latter two (the model arguments) with DI.Constant, which then translates into Enzyme.Const, so the invocation of AD is morally equivalent to

Enzyme.gradient(Reverse, batched_eval, params, Const(m), Const(y))

Since the log-likelihood term (y[1:4] ~ ...) depends on m[1:4], which in turn is derived from params[1:4], the log-likelihood should contribute to the gradient with respect to params.

However, this is unfortunately lost when we write the differentiable data from params into the non-differentiable m:

m[1:4] = params[1:4]

Since m was declared as Const, it doesn't have a 'shadow': in other words, it doesn't have a corresponding array to store its gradients in. So when we reach the log-likelihood term, Enzyme has no way of 'tracking' the gradient of the log-likelihood with respect to params.

This behaviour is intentional in Enzyme, so there isn't an 'upstream fix' available. Thus, when evaluating models with Enzyme, Wren will sometimes insert calls to _dealias at the top of the model evaluation function. (We detect when models are being run with Enzyme using the EvalContext struct, which is passed as an argument to the evaluation function.)

To see which model arguments will be copied when using Enzyme, you can call the internal WrenCore._copied_args function:

WrenCore._copied_args(model)
(:m, :y)

Eliding copies

Wren does perform some basic dataflow analysis to try to avoid copying things that definitely don't need to be copied, but this is very conservative since Wren only has access to the syntax tree. (In fact it's arguable that even this analysis is kind of pointless given the automatic optimisations described below.)

More usefully, though, Wren offers a reduce_copies function which essentially tries eliding each argument's copy one by one, and sees if the gradient (evaluated at a few points) is still correct.

new_model = WrenCore.reduce_copies(model, DEFAULT_AD)WrenCore._copied_args(new_model)
(:m,)

This costs very little time compared to Enzyme's first compilation, and so in fact when constructing a VecModel with Enzyme, this will be done automatically:

vm = VecModel(model, DEFAULT_AD)WrenCore._copied_args(vm)
(:m,)

It should be noted that this trial-and-error approach is in principle not guaranteed to always be correct. However, the cases where it will fail are extremely contrived. Essentially it requires:

  • parameter-dependent control flow, i.e., if cond(x) where x is itself a random variable;
  • the control flow must have two (or more) different paths, one of which where eliding the copy causes incorrect gradients, and one where it doesn't;
  • reduce_copies must be unlucky enough to only hit the latter path during its trial-and-error evaluation.

In general, parameter-dependent control flow already does not work well with vectorisation, so this is pretty unlikely to cause any problems in practice. However, it can be disabled with

vm = VecModel(model, DEFAULT_AD; reduce_copies=false)WrenCore._copied_args(vm)
(:m, :y)

or even more simply by just copying the argument yourself inside the model, which bypasses Wren's analysis.
